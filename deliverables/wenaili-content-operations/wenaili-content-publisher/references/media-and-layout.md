# 图片、上传与正文排版

## 封面为什么不能用文字海报

新闻热门栏是约 80×80 的正方形缩略图；主列表图片桌面宽度约占卡片 1/3，高度随文字变化；案例列表也使用 object-cover，并有悬停放大。上传 16:9 不代表展示一定 16:9。横版海报的左右标题、底部公司名会被裁掉，换成更大同版式图也解决不了。

用“无字主题封面 + 文章真实标题”分工。主体靠中间，四边留余量。中心正方形预览只能帮助判断，不能保证所有视口不裁切；最终看实际页面。信息图、数据表、长图作为正文图，必要时拆成多张，不做唯一封面。若用户坚持封面完整显示海报，说明需要开发修改图片容器/裁切策略，不在发布任务中擅改网站。

## 尺寸和体积

| 场景 | 建议尺寸（不是硬限制） | 建议体积 |
| --- | --- | --- |
| 新闻/案例封面 | 1600×900，至少约 1200×675；主体居中 | 100–350 KiB，尽量不超过 500 KiB |
| 正文照片 | 长边 1200–1600 px，保留原比例 | 每张尽量低于 500 KiB |
| 正文截图/图表 | 长边至多约 1920 px 起步，以文字可读为准；长图拆分 | 每张尽量低于 1 MiB |

服务端硬限制：附件 upload 的**整个 multipart 请求不超过 10 MiB（10×1024×1024 字节）**，文件加表单开销；不要拿恰好 10 MiB 的图片测试。运营通常应先压到 2 MiB 以下。代理可能另有更小限制，413 时继续压缩并请维护者确认，不自动调服务器上限。

照片优先 JPEG/WebP；透明图或清晰界面截图可 PNG。常规运营不上传 SVG、动画 GIF 或未知格式；不要改扩展名冒充转换。按实际工具能力转换、压缩，不无限放大低清图。输出为新文件保留原件；去除 GPS 等隐私元数据，遮挡客户信息、订单号、手机号、账号、密钥。

## 上传前检查

1. 查看图片本身，不只读文件名。确认版权/使用范围、客户授权、AI 图的适用性。
2. 记录实际像素、字节数、格式、用途、授权出处；英文短文件名如 `port-container-cover.webp`，不含敏感信息。
3. 看 1:1、16:9 和竖向裁切，关键主体不丢；在实际站点检查放大裁切效果。
4. alt 写“图中是什么以及与本文的关系”，不堆关键词，不把 AI 图描述为真实客户现场。需要来源时填 credit/creditUrl，并在文章图注保留适当说明。
5. 优先复用已授权且匹配的图片库条目。新上传后查看返回 MIME/尺寸与可访问 URL，再创建图片文档。不要混淆 attachment._id 和图片文档 _id。
6. 正文引用上传后返回的可公开稳定 HTTPS URL；不使用本地路径、临时签名地址、base64 或未授权外链。图像 URL 的读取不携带 API 密钥。

## 语义排版

标题由详情模板渲染，正文不要 h1 或重复整篇标题。用 h2 分节，h3 子节，p 段落，ul/ol 清单，blockquote 引用，figure/img/figcaption 配图；表格建议 2–4 列，移动端检查横向滚动。段落尽量短，但不为凑字数拆成每行一句。

可用样式：`article-lead` 导语、`article-note` 提示框、`article-highlight` 行内强调、`article-image-center` 居中图、`article-image-wide` 图片样式。漂浮左右图在手机退为普通流，默认不用复杂绕排。

```html
<p class="article-lead">先用一段交代读者会获得什么。</p>
<h2>本节的具体问题</h2>
<p>解释事实，<strong>只强调最重要结论</strong>。</p>
<figure>
  <img src="上传后返回的图片地址" alt="客观描述" loading="lazy" decoding="async">
  <figcaption>图片说明与必要来源</figcaption>
</figure>
<p class="article-note">需特别说明的口径或适用范围。</p>
```

正文不放 style/script/iframe、完整 html/head/body、固定大字号/固定宽高、空白占位撑高、背景渐变海报、外部字体、内联 CSS 或未经验证的 utility class。semantic 会去除 style，设计应依靠站点样式。后台富文本粘贴纯文本后应用“导语/提示框/二级标题”等现有选项，不要再套一层全页布局。
